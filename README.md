# FoodSource — сервис поиска поставщиков продуктов питания

Папка для второй части тестового задания. Здесь находится отдельный кликабельный MVP, исходный код и документация сервиса поиска и сравнения поставщиков.

> FoodSource помогает быстро найти подходящих поставщиков, сравнить условия и сохранить следующий шаг для связи.

## Что демонстрирует проект

Это не просто каталог компаний, а рабочий прототип закупочного сценария:

1. пользователь пишет запрос обычным языком — например, «яблоки от 50 кг, Екатеринбург»;
2. сервис выделяет товар, категорию, регион, доставку и минимальную партию;
3. поставщики ранжируются по объяснимым признакам;
4. пользователь проверяет контакты и качество данных;
5. подходящие карточки можно сравнить, сохранить, отметить статусом и выгрузить в XLSX.

## Что уже реализовано

- поиск по свободному запросу: категория, город/регион, доставка и минимальная партия; для продуктов учитываются синонимы (например, «яблоки» → «фрукты»);
- исправление опечаток через `RapidFuzz` и нормализация русских словоформ через `pymorphy3`;
- гибридный поиск локально и в production: квантованная ONNX-модель `rubert-tiny2` оценивает смысл запроса, а Python-фильтры сохраняют строгую проверку категории, региона и условий;
- при непустом запросе в выдаче остаются только карточки с реальным совпадением, а пустой запрос открывает весь каталог;
- отдельные поля контакта: телефон, email и адрес; пустые значения остаются пустыми;
- explainable-релевантность — у каждой карточки показаны причины совпадения;
- фильтры, сортировка, карточки поставщиков и полнота собранных данных;
- сравнение 2–4 поставщиков в одной таблице;
- статусы «Новый / Проверить / К контакту / Отобран» и заметки в SQLite;
- экспорт текущей выдачи или shortlist в настоящий XLSX с форматированной таблицей;
- импорт оператором CSV/XLSX через интерфейс и `POST /api/import/file`;
- история последних свободных поисковых запросов в SQLite через `GET /api/search-history`, с очисткой через `DELETE /api/search-history`;
- адаптивная визуальная оболочка без внешних зависимостей;
- стартовый каталог из 30 проверенных публичных источников: он создаётся из `data/sources.json`, поэтому демонстрация стабильна даже до первого сетевого обновления.
- Python API с FastAPI и SQLite: `/api/suppliers`, `/api/parse`, `/api/import`;
- API карточки хранит `phone`, `email`, `address`, `source_url` и дату обновления;
- консервативный HTML-парсер публичных страниц с сохранением ссылки на источник;
- проверка формата телефона, email, адреса и описания перед записью; сомнительные данные не перезаписывают проверенную карточку;
- очередь контроля изменений в разделе «Качество данных»: оператор видит причину, источник и принимает либо отклоняет обновление;

```text

```

Ранжирование не выдаёт непрозрачный «вердикт». В каждой карточке показываются причины совпадения: товар, категория, регион, доставка, минимальная партия и полнота данных. Синонимы товаров учитываются отдельно: например, «яблоки» связываются с фруктами, а «куриное филе» — с мясом и птицей.

### Как обрабатывается запрос

```text
Запрос пользователя
   ↓
RapidFuzz исправляет вероятные опечатки
   ↓
pymorphy3 приводит слова к нормальной форме
   ↓
словарь товаров определяет товар и допустимую категорию
   ↓
строгие правила исключают поставщиков из чужих категорий
   ↓
rubert-tiny2 переранжирует только безопасный набор кандидатов
   ↓
карточка получает оценку и понятные причины совпадения
```

Модель используется как ранжировщик, а не как источник фактов: она не создаёт поставщиков и не может протащить карточку через ограничение категории. Поэтому запрос «персики» не показывает упаковку, а «ноутбуки» возвращает пустую выдачу. В ответе `/api/search` доступны `normalized_query`, исправления запроса, причины совпадения и разбиение оценки на детерминированную и семантическую части.

### AI-поиск

Семантический слой не генерирует компании и не изменяет проверенный каталог. Он сравнивает запрос с категориями и товарами существующих карточек, после чего результат объединяется с детерминированной оценкой. Для коротких неизвестных или бессмысленных запросов действует защитный порог; при отсутствии модели API автоматически возвращается к базовому поиску.

В репозитории хранятся только production-файлы `model.int8.onnx`, `tokenizer.json` и `config.json` — около 32 МБ вместо 148 МБ полной модели. Render явно включает семантический слой через `FOODSOURCE_SEMANTIC=1` и заранее строит кэш supplier embeddings при запуске. Если ONNX Runtime или файлы модели недоступны, API безопасно возвращается к детерминированному поиску.

Локальное окружение `.venv-ai/` и исходная неквантованная модель `model.onnx` в Git не попадают. Подготовка окружения выполняется один раз:

```powershell
.\scripts\setup-local-ai.ps1
```

Если Python не находится в `PATH`, передайте полный путь:

```powershell
.\scripts\setup-local-ai.ps1 -PythonExecutable "C:\path\to\python.exe"
```

После подготовки запустите API:

```powershell
.\.venv-ai\Scripts\python.exe -m backend.run
```

Проверка статуса модели: `GET http://127.0.0.1:8000/api/search/status`. Значения `available: true` и `mode: hybrid` подтверждают, что запросы обрабатываются локальной моделью. Отключить её для сравнения можно переменной `FOODSOURCE_SEMANTIC=0`.

Модель основана на [`fissium/rubert-tiny2`](https://huggingface.co/fissium/rubert-tiny2) и распространяется по лицензии Apache-2.0. В приложение включён динамически квантованный ONNX-вариант для быстрого CPU-инференса.

Автоматические проверки поиска:

```powershell
.\.venv-ai\Scripts\python.exe -m unittest backend.tests.test_hybrid_search -v
```

Набор покрывает опечатки, словоформы, синонимы, отрицание «без доставки», food-запросы и запросы вне предметной области.

## Запуск прототипа

Из этой папки выполните любой статический сервер, например:

```bash
npx serve .
```

Затем откройте `http://localhost:3000`. Открытие `index.html` напрямую через `file://` не рекомендуется: браузер может заблокировать загрузку JSON-каталога.

Frontend и API запускаются раздельно:

```powershell
# терминал 1 — API
python -m backend.run

# терминал 2 — frontend
npx serve . -l 3000
```

## Запуск Python API

В отдельном терминале из корня `supplier-search-service`:

```bash
python -m venv .venv
.venv\\Scripts\\activate
pip install -r backend/requirements.txt
python -m backend.run
```

API будет доступен на `http://127.0.0.1:8000`, документация Swagger — на `/docs`. После запуска интерфейс автоматически переключится на SQLite-каталог и покажет форму «Подключить источник».

В блоке «Импорт от оператора» можно скачать CSV-шаблон. Поддерживаются CSV в UTF-8/Windows-1251 и XLSX до 5 МБ, максимум 1 000 строк за импорт. Обязательна колонка «Поставщик» или «Название».

Адаптивность проверена для ширины 375–430 px: фильтры становятся вертикальными, карточки — одноколоночными, сравнение прокручивается горизонтально, а модальные окна занимают доступную высоту.

## Основные API

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/suppliers` | каталог поставщиков |
| `POST` | `/api/search` | поиск и ранжирование |
| `GET` | `/api/search-history` | последние запросы |
| `DELETE` | `/api/search-history` | очистить историю |
| `PUT` | `/api/suppliers/{id}/state` | избранное, статус, заметка |
| `POST` | `/api/compare` | сравнение 2–4 поставщиков |
| `POST` | `/api/import/file` | CSV/XLSX импорт |
| `POST` | `/api/export/xlsx` | экспорт выборки |
| `POST` | `/api/parse` | разобрать публичную страницу |
| `POST` | `/api/collect` | обновить разрешённые источники |
| `GET` | `/api/pending-updates` | очередь сомнительных изменений |
| `POST` | `/api/pending-updates/{id}/approve` | принять изменение оператором |
| `POST` | `/api/pending-updates/{id}/reject` | отклонить изменение оператором |

## Подготовка к публикации

Перед деплоем:

1. не помещать API-токены, пароли и `.env` в Git;
2. вынести адрес API в переменную окружения frontend;
3. выбрать хостинг для статического frontend и отдельный хостинг для FastAPI;
4. заменить локальный SQLite на PostgreSQL, если сервис будет использоваться несколькими пользователями;
5. настроить CORS только для опубликованного домена;
6. проверить правила использования каждого внешнего источника перед автоматическим сбором.

Для демо удобно разместить frontend в Cloudflare Pages, а FastAPI — на Render, Railway, Fly.io или VPS. Cloudflare Pages не запускает Python API напрямую в таком формате, поэтому frontend и backend должны иметь отдельные адреса.

### Бесплатная публикация

1. В настройках репозитория включите **Settings → Pages → Deploy from branch → main / root**. GitHub Pages опубликует статический frontend на `https://<логин>.github.io/foodsource/`.
2. Создайте на Render бесплатный Web Service из этого репозитория. Файл `render.yaml` уже содержит build/start-команды и health-check. Имя сервиса по умолчанию — `foodsource-api`, поэтому ожидаемый адрес API — `https://foodsource-api.onrender.com`.
3. До публикации API GitHub Pages работает сразу в демо-режиме: seed-каталог загружается в браузере, доступны поиск, фильтры, избранное, сравнение и автономная XLSX-выгрузка. После создания Render-сервиса замените пустой URL в `config.js` на выданный hostname и закоммитьте изменение — интерфейс переключится на FastAPI/SQLite.

Бесплатный Render может «засыпать» после периода без запросов, поэтому первый запрос после паузы может занять несколько секунд. SQLite на бесплатном экземпляре подходит для демонстрации, но состояние избранного и заметок может сброситься после перезапуска; для постоянной многопользовательской работы нужен PostgreSQL.

## Безопасность токенов

Секреты должны храниться только в настройках GitHub Actions/Cloudflare или в локальном `.env`, который добавлен в `.gitignore`. Если токен уже был отправлен в чат, репозиторий или логи, его необходимо отозвать и создать новый.

## Автоматический сбор

Проверенные российские источники находятся в `data/sources.json`. Команда ниже последовательно обходит только этот разрешённый список, делает паузу 2 секунды между сайтами, проверяет публичность URL и `robots.txt`, сохраняет новые записи в SQLite, а результаты — в `data/collection-report.json`. Если источник запрещает обход через `robots.txt`, сервис не запрашивает страницу и использует лишь заранее проверенную карточку с прямой ссылкой на этот источник:

```bash
python -m backend.collector
```

То же действие доступно в интерфейсе кнопкой «Обновить проверенные источники» и через `POST /api/collect`. Для ежедневного запуска эту команду можно добавить в Планировщик заданий Windows.

Перед сохранением каждое автоматически извлечённое поле получает уровень уверенности. Некорректные контакты, ценовой фрагмент вместо адреса, навигационный текст и изменения средней уверенности помещаются в `pending_supplier_updates`. До ручного подтверждения старое проверенное значение остаётся в основной карточке. Очередь открывается кнопкой «Качество данных».

Для автоматического ежедневного запуска в 06:00 подготовлен сценарий:

```powershell
.\scripts\register-daily-collector.ps1
```

Можно выбрать другое время, например `.\scripts\register-daily-collector.ps1 -At 08:30`. Сценарий не создаёт новые источники сам: он обновляет только URL из `data/sources.json`.

Парсер предназначен для публичных страниц, не обходит авторизацию, CAPTCHA или ограничения сайтов. Перед промышленным сбором необходимо проверить правила использования конкретного источника.

Полный набор автоматических проверок, включая качество парсинга и безопасное обновление SQLite:

```powershell
.\.venv-ai\Scripts\python.exe -m unittest discover backend\tests -v
```
