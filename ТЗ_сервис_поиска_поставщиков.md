# Техническое задание на сервис поиска поставщиков продуктов питания

**Проект:** рабочее название «FoodSource»  
**Тип:** прототип/MVP веб-сервиса  
**Назначение:** тестовое задание для AI-инженера в Goulash.Tech  
**Версия:** 1.0, 20 октября 2026 года

## 1. Цель проекта

Разработать сервис, который помогает сотруднику HoReCa или foodtech-компании быстро найти и сравнить поставщиков продуктов, готовой продукции, упаковки и сопутствующих товаров.

Сервис должен сокращать время между формулировкой потребности и понятным следующим действием: выбрать несколько подходящих поставщиков, увидеть ключевые различия и связаться с наиболее релевантными.

Главная идея прототипа: пользователь описывает, что ему нужно, где он находится и какие ограничения важны, а сервис возвращает объяснимый список поставщиков с источниками информации, сравнением и рекомендацией.

## 2. Пользователь и сценарий

### Основной пользователь

Менеджер по закупкам, операционный менеджер, категорийный менеджер или сотрудник кухни/производства.

### Основной сценарий

1. Пользователь вводит товар или категорию: например, «замороженная куриная грудка», «крафтовая упаковка для доставки» или «овощи оптом».
2. Выбирает город/регион работы.
3. При необходимости задаёт ограничения: минимальный объём, доставка, наличие сертификата, ценовой ориентир.
4. Получает список найденных поставщиков.
5. Просматривает карточки, сравнивает 2–4 варианта и видит, почему они попали в выдачу.
6. Открывает источник, сайт или контакт и сохраняет заметку/статус «связаться».

### Альтернативный сценарий

Если точного совпадения нет, сервис предлагает близкие категории, соседние регионы или поставщиков с неполными данными, явно помечая, что нужно уточнить вручную.

## 3. Функциональные требования MVP

### 3.1. Поиск

- Поиск по свободному тексту.
- Фильтр по категории товара.
- Фильтр по городу/региону.
- Фильтр по типу поставщика: производитель, дистрибьютор, оптовик, упаковка, готовая продукция.
- Фильтр по доступности доставки.
- Фильтр по наличию сертификатов/документов.
- Фильтр по минимальному объёму заказа, если данные доступны.
- Сортировка по релевантности, региону, полноте данных и наличию контактов.

### 3.2. Карточка поставщика

Каждая карточка должна содержать:

- название;
- тип поставщика;
- категории и товары;
- регион работы;
- адрес или город, если опубликованы;
- телефон, email, сайт или форму связи, если опубликованы;
- минимальный объём заказа;
- примерную цену или ценовой диапазон, если доступен;
- условия доставки;
- сертификаты/документы;
- дату обновления данных;
- ссылку на источник;
- оценку полноты данных;
- заметку пользователя и статус: «новый», «проверить», «связаться», «отобран».

### 3.3. Сравнение

- Пользователь может выбрать от 2 до 4 поставщиков.
- Сравнение отображается в единой таблице по одинаковым полям.
- Пустые значения не заменяются выдуманными данными: показывается «не указано».
- Отличия подсвечиваются, но сервис не должен выдавать бездоказательный вердикт «лучший».
- Рекомендация формируется как объяснимый итог: например, «подходит по региону и доставке, но цену нужно уточнить».

### 3.4. Сохранение результата

- Сохранение поставщика в список «Избранное».
- Добавление заметки.
- Изменение статуса контакта.
- Экспорт выбранных поставщиков в CSV или JSON — желательно для MVP, обязательно для следующей версии.

## 4. AI-функциональность

AI не должен маскировать отсутствие данных. Его задача — улучшить поиск и объяснить результат.

### Обязательная AI-функция для прототипа

Нормализация пользовательского запроса:

```text
«Нужна куриная грудка оптом в Екатеринбурге с доставкой от 100 кг»
→ категория: мясо птицы
→ товар: куриная грудка
→ регион: Екатеринбург
→ минимальный объём: 100 кг
→ доставка: обязательна
```

### Рекомендуемые AI-функции

- извлечение фильтров из естественного языка;
- нормализация синонимов категорий и товаров;
- семантический поиск по описаниям поставщиков;
- объяснение причин попадания поставщика в выдачу;
- выявление неполных или конфликтующих данных;
- короткое резюме карточки поставщика.

### Что не делать в MVP

- не генерировать цены, сертификаты и контакты;
- не обещать юридическую проверку поставщика;
- не называть поставщика надёжным без проверяемого критерия;
- не скрывать источник информации;
- не принимать закупочное решение полностью автоматически.

## 5. Источники и сбор данных

### Вариант для демонстрационного прототипа

Использовать заранее подготовленный датасет из 20–50 обезличенных поставщиков. У каждой записи должны быть поля, источник и дата обновления. Это позволит показать логику сервиса без нестабильного внешнего парсинга на демо.

### Следующий этап

- загрузка CSV/Excel от оператора;
- ручное добавление поставщика;
- импорт из разрешённых публичных источников;
- периодическое обновление записей;
- проверка дубликатов и объединение карточек.

Любой внешний источник должен сохраняться в поле `source_url`. Необходимо соблюдать правила сайтов, robots.txt, условия использования и требования к персональным данным.

## 7. Архитектура прототипа

### Рекомендуемая схема

```text
React / Next.js UI
        ↓
FastAPI REST API
        ↓
Search service: filters + text search + optional embeddings
        ↓
PostgreSQL + pgvector
        ↓
Seed dataset / CSV importer
```

### Ответ поиска

```json
{
  "query": "куриная грудка оптом в Екатеринбурге",
  "normalized_query": {
    "category": "мясо птицы",
    "region": "Екатеринбург"
  },
  "results": [
    {
      "supplier_id": "sup_001",
      "name": "Поставщик А",
      "match_score": 0.91,
      "match_reasons": ["регион", "категория", "доставка"],
      "missing_fields": ["цена"]
    }
  ]
}
```

## 8. API MVP

### `POST /api/search`

Принимает свободный запрос и фильтры, возвращает нормализованный запрос и выдачу.

### `GET /api/suppliers/{id}`

Возвращает полную карточку поставщика и источник данных.

### `POST /api/suppliers/{id}/notes`

Создаёт заметку и статус пользователя.

### `POST /api/compare`

Принимает массив из 2–4 `supplier_id` и возвращает сравнение.

### `GET /api/categories`

Возвращает категории и синонимы для фильтров.

## 10. Варианты реализации

### Вариант A — быстрый демонстрационный MVP, рекомендуется

**Стек:** Next.js/React, TypeScript, FastAPI, SQLite или PostgreSQL, seed JSON/CSV, простой полнотекстовый поиск.

**Плюсы:** быстро собирается, легко деплоится, стабильно демонстрируется, понятен проверяющему.

**Минусы:** данные статические, нет полноценного сбора из внешних источников.

**Когда выбирать:** если цель — максимально качественно показать UX, архитектуру и бизнес-логику в рамках тестового срока.

### Вариант B — AI-поиск с семантическим ранжированием

**Стек:** Next.js, FastAPI, PostgreSQL + pgvector, embeddings, LLM для нормализации запроса и объяснения выдачи.

**Плюсы:** сильнее соответствует AI-позиции, хорошо демонстрирует RAG/семантический поиск и объяснимость.

**Минусы:** сложнее отлаживать, требуется контроль галлюцинаций и качество seed-данных.

**Когда выбирать:** если есть время на тестирование и нужно показать именно AI-компонент, а не только каталог.

### Вариант C — исследовательский прототип с импортом источников

**Стек:** Python, FastAPI, PostgreSQL, Celery/очередь, парсеры разрешённых источников, нормализация данных, админ-панель.

**Плюсы:** ближе к реальному внутреннему инструменту закупок.

**Минусы:** риски нестабильности источников, юридические ограничения, больше инфраструктуры и меньше времени на polished UX.

**Когда выбирать:** только если заранее есть разрешённые источники или собственный датасет.

## 11. Рекомендуемое решение

Выбрать гибрид **A + ограниченный слой B**:

1. Стабильный seed dataset из 30–50 поставщиков.
2. Фильтрация по структурированным полям.
3. Нормализация свободного запроса через LLM или детерминированный parser с fallback.
4. Объяснимый `match_score`, основанный на совпадениях полей, а не на выдуманном рейтинге.
5. Сравнение и заметки как основное пользовательское действие.
6. Источник и дата данных в каждой карточке.

Такой формат показывает одновременно продуктовую логику, Python/API, AI-автоматизацию, работу с данными и самостоятельное проектирование MVP.

## 12. Безопасность и качество данных

- Контакты брать только из разрешённых публичных источников или подготовленного датасета.
- Не хранить пароли, токены и ключи в репозитории.
- Валидировать email, URL, телефон, числовые поля и регион.
- Показывать дату обновления и источник.
- Разделять `unknown`, `not_provided` и `not_applicable`.
- Логировать ошибки импорта и не перезаписывать хорошие данные пустыми значениями.
- Для AI-ответов использовать только контекст найденных записей.

## 14. Критерии приёмки

- Пользователь может выполнить поиск по категории и региону.
- Выдача содержит минимум 10 демонстрационных поставщиков.
- Каждая карточка содержит название, категорию, регион, контакт/сайт или честную отметку об отсутствии данных, источник и дату обновления.
- Можно выбрать 2–4 карточки и сравнить их.
- Можно сохранить заметку и статус поставщика.
- Свободный запрос отображается в нормализованном виде.
- AI не создаёт факты, которых нет в датасете.
- Интерфейс корректно работает на мобильном и десктопе.
- README содержит запуск, архитектуру, структуру данных, ограничения и ссылки на демо.
- Демо запускается без ручной настройки секретов или содержит понятную инструкцию для `.env`.
